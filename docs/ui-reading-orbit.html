当接口设计里“游客可读”和“登录可写”共存时，最容易出问题的不是业务代码，而是鉴权链路中默认拦截的那一层。

为什么要调整阅读页结构

你的项目本身已经有文章列表、详情和后台内容管理能力，但页面更偏传统博客模板。这个概念稿把阅读页设计成一种“阅读轨道”，让用户在打开文章后，能持续感知当前位置、目录结构、作者信息和系列上下文。

对于技术博客尤其有价值，因为技术文章往往更长，访客并不是看完一屏就走，而是需要在正文、目录、示例和相关推荐之间来回跳转。

阅读页不该只是正文容器，它应该是帮助用户理解上下文的界面。

游客可见接口与鉴权边界

如果你已经在后端层面把文章查询接口设为了游客可访问，但浏览器依然拿到 401，通常要优先检查两件事：接口是否真的落在匿名白名单内，以及前端请求拦截器是否在没有 token 时主动加了错误的头部或跳转逻辑。

前端侧风险 axios 拦截器默认要求登录，导致所有 `/api/*` 请求都进入同一套鉴权逻辑。
后端侧风险 Spring Security 或自定义过滤器把文章列表接口遗漏在白名单外。

前端拦截器的常见误判

许多博客项目会在请求层统一附带 token，并且在 401 时直接弹出登录提示。这本身没问题，但如果没有区分“公开内容接口”和“需要登录接口”，游客访问文章列表时也会被当成异常状态处理。

一个更稳妥的方式，是针对文章列表、文章详情、分类查询这类公共资源单独维持访问白名单，至少不要在前端层面强制它们依赖 token。

后端白名单与权限注解

如果后端用了统一鉴权配置，还要继续确认路径是否完全匹配。常见问题是后端白名单写成了某个旧路径，前端实际请求却走了代理后的新路径，于是你以为“文章接口已开放”，但网关或过滤器看到的是另一个地址。

这类排查最好按顺序做：先看浏览器实际请求地址，再看前端代理映射，再看后端 controller 路径，最后核对 security 配置。顺序反了，很容易陷进“明明已经放行”的错觉里。

最终排查顺序

先验证接口地址，再验证前端拦截器，再验证后端匿名放行配置，最后才看数据库或业务逻辑。401 是鉴权失败，不是数据问题，因此没必要一开始就怀疑 SQL 或实体映射。
